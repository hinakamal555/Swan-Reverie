# Template Editor Starter Kit

A reusable factory for **interactive wedding invitation editors** sold as digital products (e.g. on Etsy).

Each design is a **separate deploy** with its own URL. Buyers sign in, customize their invitation in the browser, publish, and share `/i/{publicId}` with guests. **Guest invitation pages stay public** — only the editor and RSVP inbox require sign-in.

---

## Why this repo exists

HoneyBee Studio started as one app with many templates. That works for a unified platform, but it is the wrong shape for **Etsy-style digital sales**:

| Unified platform | This starter kit |
|------------------|----------------|
| One site, many templates | **One site per design** |
| Template picker / entitlements | Buyer gets **one link** for their purchase |
| Shared URL space | **Natural isolation** between products |
| Auth, admin, catalog | **Clerk sign-in** — manage invitations + RSVP inboxes |

The idea: **never rebuild the editor for each new design**. Build it once in `core/`, then ship new products by swapping only `template/`.

```
┌─────────────────────────────────────────────────────────┐
│  template-editor-starter-kit (this repo)                │
│                                                         │
│   core/          ← editor engine (shared, stable)       │
│   template/      ← one design (visuals + content schema)│
│   scripts/       ← assemble → site/                     │
└─────────────────────────────────────────────────────────┘
                          │
                          ▼ assemble
┌─────────────────────────────────────────────────────────┐
│  site/  →  deploy to Netlify  →  etsy-product-url.com │
└─────────────────────────────────────────────────────────┘
```

**One Etsy listing = one GitHub repo (or fork) = one Netlify site = one `template/` folder.**

---

## How it works

1. **`core/`** — Express API, MongoDB persistence, editor UI, guest runtime (gatefold, countdown, RSVP, etc.). Do **not** edit per design unless fixing a bug for all products.

2. **`template/`** — Everything unique to one invitation design:
   - `config.json` — identity, site title, **which editor sections appear**
   - `defaults.js` — default invitation content
   - `render.js` — HTML/layout for the guest invitation
   - `styles.css` — design-specific CSS
   - `assets/` — images, audio

3. **`npm run assemble`** — Merges `core/` + `template/` into `site/` (the deployable app).

4. **Deploy `site/`** to Netlify with env vars from `.env.example`.

## Copy this repo for a new design (checklist)

**Yes — duplicate the repo, change only `template/`, deploy.** Auth, dashboard, RSVP inboxes, and invitation naming live in `core/` and work automatically on every copy.

### Step-by-step

1. **Duplicate this repo on GitHub** → e.g. `invitation-english-chateau`
2. **Clone locally** and copy env vars:
   ```bash
   cp .env.example .env
   ```
   Set `MONGODB_URI`, `CLERK_PUBLISHABLE_KEY`, and `CLERK_SECRET_KEY` (reuse the same Clerk app keys across all designs — see below).
3. **Replace everything in `template/`** — the only folder that changes per design:
   - `config.json` — new `templateId`, `name`, `siteTitle`, **`brandName`**, editor sections
   - `defaults.js` — sample content for this design
   - `render.js` — guest invitation HTML/layout
   - `styles.css` — design-specific CSS
   - `assets/` — images, music
4. **Test locally:**
   ```bash
   npm run dev
   ```
   Opens http://localhost:8888 → sign in → create invitation → edit → publish.
5. **Push to GitHub** → connect a **new Netlify site** → set env vars from `.env.example`
6. **Add the new Netlify URL** in Clerk → Domains / Allowed redirect URLs
7. **Put the live URL** in your Etsy download PDF

### What you do NOT change per design

| Folder / file | Per design? |
|---------------|-------------|
| `template/` | **Yes — this is the design** |
| `core/` | No — shared engine (auth, editor, API, RSVP) |
| `scripts/` | No |
| `site/` | Never edit — regenerated by `npm run assemble` |
| Clerk app | Reuse one app; add each new domain |
| MongoDB | Can reuse one cluster (invitations scoped by user + `templateId`) |

## Authentication and invitation management (built into `core/`)

Every copy of this repo includes:

| Feature | Where |
|---------|--------|
| Sign-in (Clerk) | `/` and `/editor/{id}` |
| Invitation dashboard | `/` — list, create, delete |
| Invitation naming | Editor → **Name** section (dashboard label; guests never see it) |
| RSVP inbox | Editor → **Replies** panel (per invitation) |
| Guest invitation | `/i/{publicId}` — public, no login |

Buyers sign in once, manage multiple invitations, and each invitation has its own RSVP inbox. Guest pages stay public.

**One Clerk app for all designs:** use the same `CLERK_PUBLISHABLE_KEY` and `CLERK_SECRET_KEY` on every Netlify deploy. Add each new domain in the Clerk dashboard.

## Editor sections (per design)

Not every design needs every editor panel. Control visibility in `template/config.json`:

```json
{
  "editor": {
    "sections": ["couple", "cover", "intro", "when", "events", "rsvp", "closing", "publish"]
  }
}
```

| Section ID | Editor panel | Typical use |
|------------|--------------|-------------|
| `couple` | Bride & groom names | Almost always |
| `cover` | Hero text, date, timezone | Almost always |
| `intro` | Opening paragraph | Narrative designs |
| `when` | Countdown + scratch cards | Save-the-date reveal |
| `events` | Multi-day schedule | Weekend weddings |
| `journey` | Travel / coach info | Destination weddings |
| `media` | Background music | Optional ambience |
| `rsvp` | Guest replies | When collecting RSVPs |
| `closing` | Final line | Sign-off text |
| `publish` | Share link | Always included automatically |

Omit sections the design does not use. The editor hides those panels; `render.js` should not render matching blocks (or gate them with `content.*.enabled` flags).

## Template config reference

`template/config.json`:

```json
{
  "templateId": "classic-floral-01",
  "name": "Classic Floral",
  "version": "1.0.0",
  "siteTitle": "Classic Floral Invitation Editor",
  "brandName": "HoneyBee Studio",
  "supportedFeatures": ["gatefold", "countdown", "scratch", "events", "rsvp", "music"],
  "editor": {
    "sections": ["couple", "cover", "intro", "when", "events", "journey", "media", "rsvp", "closing", "publish"],
    "features": []
  }
}
```

- **`templateId`** — Unique slug (lowercase, hyphens). Used in MongoDB and JS registry.
- **`siteTitle`** — Browser tab title and editor page title.
- **`brandName`** — Shown in the dashboard eyebrow and editor header (e.g. `HoneyBee Studio`). Set this per design repo if you use a different studio name.
- **`supportedFeatures`** — Documented capabilities; keep in sync with what `render.js` implements.
- **`editor.sections`** — Which sidebar panels appear for this design.

The **Invitation name** field in the editor is separate from `config.json` — buyers set it per invitation so they can tell drafts apart on the dashboard. If left blank, it shows as **Unnamed invitation**.

## Deploy to Netlify

1. Push repo to GitHub
2. **Add site** → import repo
3. Build settings come from `netlify.toml`:
   - Build: `node scripts/assemble.js && cd site && npm install`
   - Publish: `site/public`
   - Functions: `site/netlify/functions`
4. Set environment variables from `.env.example`
5. MongoDB Atlas → Network Access → allow `0.0.0.0/0`
6. Clerk → add your Netlify domain(s) under **Domains** and **Allowed redirect URLs**

### Clerk setup (one app for all designs)

Use **one Clerk application** across every design deploy:

1. Create an application at [dashboard.clerk.com](https://dashboard.clerk.com)
2. Copy **Publishable key** and **Secret key** into each site's env vars
3. Add every Netlify URL you deploy (e.g. `https://classic-floral.netlify.app`, `http://localhost:8888`)
4. Reuse the same MongoDB cluster if you want — invitations are scoped by `ownerId` (Clerk user) and `templateId`

When you duplicate this repo for a new design, **keep the same Clerk keys** unless you want a completely separate user base.

## Content schema (what the editor saves)

The editor reads/writes a JSON `content` object. Key paths used by the default editor:

```
content.couple.{brideName, groomName}
content.weddingDateTime.{date, startTime, timezone}
content.text.{heroLabel, heroLocation, introHeading, introBody, ...}
content.scratch.{enabled, cards[], completionText}
content.events[] — {title, kicker, venue, address, date, times, mapsUrl, colors}
content.journey.{enabled, title, subtitle, departLine, ...}
content.media.{musicUrl, heroImageUrl}
content.rsvp.{enabled, deadline, attendanceOptions, notificationEmails}
content.location.{venue, address, mapsUrl}
content.theme.{colors}
```

`defaults.js` must define every field `render.js` reads. Fields not exposed in the editor keep their defaults unless you extend `core/` (rare).

## Assets

Place files in `template/assets/`. Reference as `/assets/filename.jpg` in `defaults.js` and `render.js`.

Example template expects: `hero-archway.jpg`, `gate-left.jpg`, `gate-right.jpg`, `wax-seal.png`, `floral-urn.png`, `sample-music.mp3`. Add your own before publishing.

## Updating the shared engine

When you fix a bug in `core/`:

1. Fix here in the starter kit
2. Copy updated `core/` into each live design repo (or re-fork and re-apply `template/`)

Never fork the entire editor per design.

---

## What NOT to do

- Do not copy `editor.js` / `runtime.js` into each design repo
- Do not put multiple templates in one deploy (defeats the Etsy isolation model)
- Do not edit `site/` directly — run `npm run assemble` or `npm run dev` (dev runs assemble first)
- Do not commit `.env` or secrets
- Do not re-implement Clerk auth per design — it is already in `core/`

## Environment variables (every deploy)

| Variable | Required | Purpose |
|----------|----------|---------|
| `MONGODB_URI` | Yes | Database connection |
| `MONGODB_DB` | Optional | Database name (default from URI) |
| `CLERK_PUBLISHABLE_KEY` | Yes | Clerk sign-in (browser) |
| `CLERK_SECRET_KEY` | Yes | Clerk sign-in (server) |
| `PUBLIC_ORIGIN` | Recommended | Full URL for copy-link fallbacks |
| `CLOUDINARY_URL` | Optional | Production media uploads |
